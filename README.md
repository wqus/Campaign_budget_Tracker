# Campaign Budget Tracker

API на Django + DRF для учёта бюджетов рекламных кампаний.
Проект сделан, чтобы применить паттерны из продакшен-разработки
(идемпотентные операции записи, безопасные конкурентные обновления,
выделение сервисного слоя) уже в стеке Django/DRF.

## Зачем этот проект

Домен — кампании с бюджетом, который постепенно расходуется — намеренно
упрощённый срез личного кабинета рекламодателя. Интересна тут не CRUD-часть,
а единственный эндпоинт, который реально списывает деньги:
`POST /campaigns/{id}/spend/`. Он должен быть безопасен при повторных
запросах и при параллельных обращениях. Подробности — в разделе
[Технические решения](#технические-решения) ниже.

## Стек

Python 3.12 · Django 5 · Django REST Framework · PostgreSQL 16 (SQLite —
для локальной разработки без Docker) · pytest · Docker / docker-compose

## Запуск

### Вариант A — Docker (рекомендуется, конфигурация приближена к продакшену)

```bash
cp .env.example .env
docker compose up --build
```

API будет доступно по адресу `http://localhost:8000/api/v1/`.

### Вариант B — локально, без Docker (автоматически использует SQLite)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Для этого варианта переменная `DATABASE_URL` не нужна — `config/settings.py`
сам переключается на локальный файл SQLite, если она не задана.

## Запуск тестов

```bash
pytest
```

По умолчанию запускается с подсчётом покрытия (см. `pytest.ini`). Один
тест — `test_concurrent_spends_never_overdraw_budget` — пропускается на
SQLite, потому что SQLite не поддерживает настоящую блокировку строк между
соединениями. Он рассчитан на запуск против Postgres:

```bash
docker compose run --rm web pytest
```

## Обзор API

| Метод | Эндпоинт | Описание |
|---|---|---|
| GET | `/api/v1/campaigns/` | Список кампаний. Фильтрация: `?status=active`, `?advertiser_name=...`, поиск: `?search=...` |
| POST | `/api/v1/campaigns/` | Создать кампанию |
| GET | `/api/v1/campaigns/{id}/` | Получить кампанию |
| PATCH | `/api/v1/campaigns/{id}/` | Обновить поля кампании (кроме статуса) |
| DELETE | `/api/v1/campaigns/{id}/` | Удалить кампанию |
| POST | `/api/v1/campaigns/{id}/activate/` | Перевести в статус `active` (отклоняется, если бюджет исчерпан) |
| POST | `/api/v1/campaigns/{id}/pause/` | Вернуть в статус `draft` |
| POST | `/api/v1/campaigns/{id}/spend/` | Списать бюджет (ключевой эндпоинт — см. ниже) |

### Пример: списание бюджета

```bash
curl -X POST http://localhost:8000/api/v1/campaigns/<id>/spend/ \
  -H "Content-Type: application/json" \
  -d '{"amount": "150.00", "idempotency_key": "order-42"}'
```

`idempotency_key` — значение, которое контролирует клиент и может повторно
использовать при ретрае (например, ID заказа или UUID, сгенерированный один
раз на конкретное действие пользователя).

## Технические решения

**Идемпотентность.** Эндпоинт `spend/` требует `idempotency_key`. Если
запрос с тем же ключом приходит повторно — например, клиент делает ретрай
после таймаута, не зная, прошёл ли первый запрос — второй вызов вернёт уже
существующую транзакцию вместо повторного списания. Это обеспечивается и на
уровне логики приложения (проверка перед записью), и на уровне БД
(уникальное ограничение на `idempotency_key`), поэтому даже гонка между
двумя одинаковыми ретраями не приведёт к двойному списанию.

**Конкурентность.** Два разных запроса, списывающих бюджет с одной и той же
кампании одновременно, не должны оба пройти, если в сумме они превышают
бюджет. `spend_budget()` оборачивает проверку и обновление в
`transaction.atomic()` и берёт блокировку строки через
`select_for_update()` на кампании — второй запрос дожидается коммита
первого и затем перепроверяет уже обновлённый остаток, вместо того чтобы
оба запроса прочитали устаревший баланс и оба прошли.

**Почему выделен сервисный слой.** В `campaigns/services.py` вынесена вся
бизнес-логика, изменяющая состояние (`spend_budget`, `activate_campaign`,
`pause_campaign`); views остаются тонкими адаптерами запрос/ответ. Это
повторяет разделение Handlers → Services → Repositories, использованное и в
других проектах — оно позволяет тестировать важные правила без поднятия
HTTP-запросов и не даёт `PATCH`-запросу незаметно изменить `status` в обход
этих защищённых путей.

**Почему `spent_total` хранится прямо на кампании**, а не всегда
суммируется из строк `SpendTransaction`: проверка бюджета в горячем пути
становится одним чтением индексированной строки под блокировкой, а не
агрегирующим запросом. Таблица транзакций при этом остаётся как аудиторский
след и как источник проверки идемпотентности.

```
├── Dockerfile
├── requirements.txt
└── .github/workflows/ci.yml
```

## Что осознанно не входит в проект

Это фокусный pet-проект, а не полноценная рекламная платформа — здесь нет
аутентификации, рекламных креативов, таргетинга или rate limiting. Цель была
показать один нетривиальный кусок backend-логики, сделанный качественно, а
не широкий, но поверхностный набор фич.
